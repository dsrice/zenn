## バインディングとは

SAMLメッセージを実際のトランスポートプロトコル（HTTP、SOAP等）でどうやって曹純するかの方法を定義したものである。

## 主要なバインディング

### HTTP Redirect Binding

よく使われるのはAuthnRequestの送信に利用される

仕組みとしては

```
SP → User's Browser → IdP

手順：
1. SPがAuthnRequestを生成
2. Base64エンコード + Deflate圧縮
3. URLのクエリパラメータに埋め込む
4. ブラウザをIdPにリダイレクト
```

となる。
処理の流れとしては

```
SP                          Browser                     IdP
 |                             |                          |
 | ①AuthnRequest生成           |                          |
 | ②Base64 + Deflate           |                          |
 |                             |                          |
 | ③302 Redirect               |                          |
 | Location: https://idp...    |                          |
 | ?SAMLRequest=PHNhbW...      |                          |
 |---------------------------->|                          |
 |                             |                          |
 |                             | ④GET /sso?SAMLRequest=...|
 |                             |------------------------->|
 |                             |                          |
 |                             |                          | ⑤解凍・パース
 |                             |                          | ⑥処理
 |                             |                          |
```

SPが未認証状態であるったときにIdpにリダイレクトしてもううときの処理になります。
一般的には、認証してもらうときの認証画面はIdp側の容易になるのでブラウザ上では遷移してもらう必要があるのでリダイレクト方式が採用されることが一般的になっています。この方式のメリット、デメリットをまとめると以下のようになります。

#### メリット

```
✓ シンプル（GETリクエストのみ）
✓ ブラウザの「戻る」ボタンが動作する
✓ 実装が簡単
✓ ブックマーク可能（RelayStateまで含めて）
```

#### デメリット

```
❌ URLの長さ制限（通常2KB〜8KB）
❌ サイズの大きいメッセージは送れない
❌ URLがログに残る（セキュリティ上の懸念）
❌ 署名を含めるとさらに大きくなる
```

### HTTP POST Binding

主な用途としてはResponse（認証レスポンス）の送信に使われます。
仕組みとしては

```
IdP → User's Browser → SP

手順：
1. IdPがResponseを生成
2. Base64エンコード（圧縮なし）
3. HTMLフォームの隠しフィールドに埋め込む
4. JavaScriptで自動POST
```
となる。
処理の流れとしては、

#### HTTP POST Bindingの流れ

```
IdP                         Browser                      SP
 |                             |                          |
 | ①Response生成               |                          |
 | ②署名                       |                          |
 | ③Base64エンコード           |                          |
 |                             |                          |
 | ④200 OK (HTML)              |                          |
 | <form method="post"...>     |                          |
 | <input name="SAMLResponse"  |                          |
 |        value="PHNhbW...">   |                          |
 |---------------------------->|                          |
 |                             |                          |
 |                             | ⑤JavaScript自動POST      |
 |                             | POST /acs                |
 |                             | SAMLResponse=PHNhbW...   |
 |                             |------------------------->|
 |                             |                          |
 |                             |                          | ⑥デコード
 |                             |                          | ⑦署名検証
 |                             |                          | ⑧処理
 |                             |                          |
 ```

認証レスポンスとしては使われることが一般的には多い方式です。
よく使われていた背景として強いのは、ブラウザ問題です。
今のブラウザでは解消されていますが、昔（特にIE）では、URLの長さに文字数制限がありました。
レスポンスにデジタル著名をすると文字列が長くなりクエリパラメーターとして付与できずにエラーになってしまう恐れがあったために回避策としてよく利用されていました。
メリット、デメリットをまとめると

#### メリット

```
✓ サイズ制限なし（大きなメッセージも送信可能）
✓ URLにデータが含まれない（ログに残らない）
✓ デジタル署名を含められる
✓ 実装が比較的簡単
```

#### デメリット

```
❌ ブラウザの「戻る」ボタンで再POSTされる
❌ ブックマークできない
❌ JavaScriptが必要（noscriptで対応可能）
```

### HTTP Artifact Binding

主な用途としては、セキュリティを重視する環境で使われます。
先ほどの２つとは違って通信経路が異なります。

仕組みとしては、

```
IdP → Browser → SP
         ↓
      (Artifact参照のみ)
         ↓
SP → IdP (バックチャネル/SOAP)
  ← アサーション本体
```

#### Artifactの構造

```
Artifact = 短い参照文字列（約44バイト）

構造：
- TypeCode（2バイト）
- EndpointIndex（2バイト）
- SourceID（20バイト）：IdPのハッシュ
- MessageHandle（20バイト）：ランダム

例：
AAQAADWNEw5VT47wcO4zX/iEzMmFQvGknDfws2ZtqSGdkNSbsW1cmVR0bzU=
```

通信経路が先の２つより複雑になっているために利用されてる実態が少ない方式です。
SOAPなどBE同時で通信する方法が必要になるので一部のサービスでしか利用できなかったりと使うまでの課題がたくさんある方式になります。
メリット、デメリットを並べると

#### メリット

```
✓ 最高のセキュリティ
✓ アサーションがブラウザを経由しない
✓ URLが短い
```

#### デメリット

```
❌ 実装が複雑
❌ バックチャネル通信が必要
❌ SOAP対応が必要
❌ ほとんど使われない
```
